# Rust build and feedback audit (2026-10-01)

This is an audit of the post-maintenance code, not a proposal for another blanket dependency cleanup. The short answer: **the slowest required CI path is published Canvas contract execution, not a known slow crate**. The most expensive measured Rust build is the public service Dockerfile's all-binary release layer. Start by removing a proven duplicate test execution, then make that public builder reuse dependency compilation. Do not choose a crate split or version migration until Cargo unit timings show it is on the critical path.

The snapshot is UI `737a52e1e0198f3953304f4bf446e90b8f98b7f1`, Core `73f6d5898b2147d0ab4f7cca318c76006a2fa3d6`, and MMF `c55d323e6aa64cad4f49308792f1d21eaab0ebc8`. Commands, run IDs, and log-derived figures are in [the evidence appendix](rust-build-audit-evidence.md). No clean/full build, test suite, cache clearing, or compilation probe was run for this audit (0 of 2 allowed probes); the existing runs already distinguish the first priorities. No per-crate Cargo timing report was available, so this report does **not** rank compilation units by guessed duration.

## Confirmed structural opportunities, not measured savings

1. **Selected Canvas tests execute twice.** `run-db-contract-groups.py preflights` runs four exact tests from the same `canvas_published_schema_contract` executable. Later `run-published-canvas-contracts.sh` runs the full executable with only the SQL-logging test skipped, so those four are included again. The early preflights are useful diagnostics; the duplicate full-suite invocation is avoidable if the full suite can verify that all four preflights already passed in this job. The job log records 250 disposable PostgreSQL and migration-probe starts across these phases. Each test's isolation/provenance must remain intact.
2. **The public Docker build loses reuse on a source edit.** `services/Dockerfile` copies all of `rust/`, `proto/`, and `contracts/` before a single release `RUN`; any change to copied input invalidates that layer. It has no chef dependency layer or compiler cache, and the release action has no external BuildKit cache declaration. CI's `Dockerfile.ci` already uses chef, sccache and GitHub BuildKit caching, but its builder is a separate job and different Dockerfile. The shared public image deliberately contains all binaries; do not remove required binaries to make its build appear faster. What is avoidable is recompiling unchanged dependency work on a warm source-only build.
3. **Multiple Core generations coexist in the application.** A locked Linux `cargo tree -e normal,build` for `marty-issuance-service` shows `marty-crypto` 0.1.62 directly and through old OID4VCI/verification, plus `marty-crypto` 0.2.0 through `marty-emrtd-issuance` for `prepare_sod`. This is real duplicated codegen potential, but no timing report proves it is on the wall-clock critical path. Replacing 0.1.62 with Core 0.2 crosses removed private-key/local-crypto APIs and needs a separate behavior/security migration.

Feature unification prevents a quick Cedar win: the same production graph reaches `cedar-policy` through **both** pinned `marty-verification` and focused MMF `mmf-security`. Multiple UI services also enable MMF's Cedar feature. Disabling one manifest edge would not remove Cedar from the selected build, and policy functionality is in use. The 13 inspected UI service `build.rs` files declare specific proto `rerun-if-changed` inputs; no blanket rerun or content-rewrite trigger was established. These are not justified optimization PRs yet. [Cargo's build-script rules](https://doc.rust-lang.org/cargo/reference/build-scripts.html) and [feature-unified tree semantics](https://doc.rust-lang.org/cargo/commands/cargo-tree.html) explain why manifest text alone is insufficient.

## First three PRs

1. **Deduplicate the four preflights from the later full Canvas execution** (`marty-ui`: `scripts/ci/run-db-contract-groups.py`, `scripts/ci/run-published-canvas-contracts.sh`, and focused script tests). Keep the early four exact tests and the full suite's other tests. Write a same-job success marker only after all preflights pass; make the full invocation omit exactly those four only when it validates that marker against the executable/test list. Direct `full` runs without that marker must still run everything. This removes four repeated end-to-end cases and their owned Docker setup from the CI critical path; it eliminates **no compilation**. Confidence: high that duplication exists, medium on wall-clock effect because the tests overlap at two threads. Risk: accidentally skipping tests when preflight evidence is absent; validate fail-closed behavior, exact test-list coverage, and the existing merge-queue suite.
2. **Bring dependency compilation reuse to the canonical public service builder** (`marty-ui`: `services/Dockerfile`, `scripts/build-rust-service-binaries.sh`, `.github/workflows/ci.yml`, `.github/workflows/cd.yml`, and existing packaging checks). Preserve Rust 1.95 Bookworm, the default release profile, all current binaries, image contents, SBOM/provenance, and the opt-in feature variant. Use the already adopted cargo-chef/sccache/BuildKit approach and GitHub cache backend, with PRs read-only and trusted main/release writes; do not add a new cache service or change production linker flags just to force cache sharing. This should make unchanged third-party/native and first-party dependency compilations reusable across **warm** source-only public builds; it does not eliminate a genuinely cold build or final binary linking. Confidence: high in invalidation, medium in warm-build benefit pending measured cache reuse. Security/maintenance risk: cache credentials, reproducibility and image parity; validate Dockerfile contract tests, compare binary list/digests and release metadata, run one normal protected CI/release qualification path, and inspect layer + cache stats.
3. **Land the additive timing/cache evidence patch prepared with this audit** (`marty-ui`: `.github/workflows/ci.yml`, `scripts/ci/sanitize_sccache_stats.py`, `tests/test_sanitize_sccache_stats.py`). It adds Cargo `--timings` only to the existing `--no-run` compilation, uploads the current timing HTML and allowlisted numeric sccache counters for two days, and keeps all checks. It removes no work now. Use the next normal CI run to identify the actual compiler-unit critical chain before proposing a first-party crate split, duplicate-version migration, or linker/profile change. Confidence: high in diagnostic value; risk: public artifact disclosure/storage, mitigated by a strict counter allowlist, no raw environment/path capture, and short retention. Validate script unit tests, workflow syntax, and normal CI. [Cargo timings](https://doc.rust-lang.org/cargo/reference/timings.html) report unit duration, concurrency and unblocking relationships, unlike `cargo check` or ordinary compile-log gaps.

PR 1 targets **CI feedback and total runner work**. PR 2 targets **warm CI public-image builds, release builds, and local Docker rebuilds**; it is not a claim about a cold cache. PR 3 measures **test-executable compilation** and cache behavior; it has no direct speed-up. Local non-Docker incremental edits and the CI-only image path remain separate, unmeasured optimization questions.

## Do not prioritize yet

- Broad `p256`/`sha2`/`hmac`/`rand` alignment, Core 0.1-to-0.2 migration, or further Cedar/Redis feature removal: compatibility and security work are real, but no current Cargo timing evidence shows a meaningful feedback win, and Cedar has multiple active enablers.
- Another cache backend, `cargo-hakari`, target-directory sharing across jobs, or more release profile/linker changes: no measured failure justifies the extra complexity. The public Docker builder has a specific reuse gap to address first.
- Rewriting proto build scripts or splitting `marty-issuance-service` solely because it is large: no broad rerun trigger or compilation-unit critical path has been demonstrated.
- Raising Canvas `--test-threads` or distributing tests to more runners without proving resource safety and exact coverage. The four known duplicate cases are a smaller, safer first correction.

**First action:** keep the valuable preflight gate but stop running its four successful cases again in the full Canvas suite. That addresses the measured CI critical path without dropping a test. It avoids repeated Docker-backed test work, **not Rust compilation**. For compilation specifically, the first justified change is public Docker builder reuse: the timed 919/1,066-second all-binary release layers currently recompile unchanged dependencies after source-layer invalidation; a shared chef/sccache-backed dependency stage can avoid that work on warm builds while retaining production binaries and checks.
