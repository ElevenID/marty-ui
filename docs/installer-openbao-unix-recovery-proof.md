# OpenBao Unix control and expired TCP certificate recovery proof

The opt-in test in [`tests/test_openbao_unix_tls_recovery.py`](../tests/test_openbao_unix_tls_recovery.py)
demonstrates that an already initialized, unsealed **official OpenBao 2.5.5
process** can authenticate an operator through a restricted Unix socket, sign a
replacement TCP certificate under its existing internal PKI issuer, and reload
that certificate with `SIGHUP` while normal TCP certificate verification is
failing because the previous leaf expired.

This is an interface proof. It does not change the installer's HTTP client,
OpenBao configuration, deployment, or accepted recovery commands.

## Run the isolated proof

Use Linux, Python with `cryptography`, and an independently verified official
OpenBao 2.5.5 binary. The test checks the reported version and build commit,
records the binary SHA-256, and skips ordinary test collection unless explicitly
enabled:

```sh
MARTY_OPENBAO_UNIX_PROOF_BINARY=/absolute/path/to/bao \
  python3 tests/test_openbao_unix_tls_recovery.py -v
```

The caller must be allowed to create loopback TCP and Unix sockets. The proof
creates an owned temporary directory under `/tmp`, starts one non-dev OpenBao
process with temporary file storage, and always terminates that process and
removes the fixture. It does not use Docker, a cloud account, an external CA,
ambient OpenBao credentials, or a changed host clock. Root execution additionally
tests that a child dropped to UID/GID 65534 cannot connect to the operator socket;
an ordinary owner run reports that cross-UID check as unexercised while still
checking socket and directory ownership and modes.

Each request has a three-second socket timeout. The old test leaf lasts 15
seconds, its natural expiry wait is bounded to 20 seconds, and startup/reload
observations each have a ten-second deadline. The successful observed run took
**15.316 seconds**.

## Observed sequence and assertions

| Step | Required observation |
| --- | --- |
| Start the isolated process | A Unix API socket owned by the operator, mode `0600`, inside a `0700` directory; a separate TCP TLS listener on loopback. |
| Initialize the fixture once | Generate an internal PKI issuer, a constrained signing role, and a scoped AppRole. Revoke the bootstrap root token and verify that it now receives HTTP 403. |
| Establish the baseline | Authenticate with the AppRole, sign a 15-second leaf, publish its public chain, reload, and complete a normally verified TLS request. |
| Let that leaf expire | A fresh TCP connection fails with `SSLCertVerificationError` and OpenSSL verification code **10**, specifically certificate expiry. |
| Use the operator socket during expiry | A fresh AppRole login succeeds. An unauthenticated signing request, mount inspection, and new-root generation remain forbidden. The original internal issuer key metadata is unchanged. |
| Sign and publish a replacement | The new leaf has the same node public key and issuer and a different serial number. Atomic publication alone leaves the running TCP listener on the expired leaf. |
| Send `SIGHUP` to the owned process | A fresh, fully verified TCP connection receives the exact new certificate. Authenticated TCP API access works again, with unchanged process ID, cluster ID, trust anchor, and node key file. |

The proof records exactly one initialization call. The recovery section performs
no initialization, unseal, or bootstrap-root operation. All TLS clients retain
`CERT_REQUIRED` and hostname verification; no insecure-TLS flag or alternate
unverified network connection is used. The Unix socket is a local authenticated
API transport protected by filesystem access controls.

The signing policy names one PKI role and one existing key metadata path. It
allows only the fixture identity (`localhost`, `127.0.0.1`), the explicit CSR
operation, and the two short test TTLs. It grants no mount management, policy
administration, new issuer creation, or broad `sys/*` permission. AppRole
credentials and returned client tokens remain in test process memory; they are
not printed or included in the evidence JSON.

## The two key custody boundaries

The **issuing CA key** is generated by `pki/root/generate/internal`. OpenBao's
version-pinned API documentation states that an internal key is not returned and
cannot subsequently be retrieved. The proof verifies that the creation response
contains no private key and that the same issuer key metadata is used for both
certificates. [OpenBao 2.5.5 PKI API source](https://github.com/openbao/openbao/blob/v2.5.5/website/content/api-docs/secret/pki.mdx)

The **TCP listener's leaf key is file-backed**. The official binary's file
certificate path constructs a reloadable getter from `tls_cert_file` and
`tls_key_file`; its alternative ACME implementation also uses ordinary key
generation and file storage. The official listener does not expose the Marty
remote-Transit TLS signing interface. This proof retains the same node key file
and replaces only the public certificate chain; it does not claim a nonexportable
leaf key. [OpenBao 2.5.5 certificate getter source](https://github.com/openbao/openbao/blob/v2.5.5/internalshared/listenerutil/tls_acme.go)

The existing Marty `selfhost-tls-init` also keeps a PEM node key inside the
OpenBao state volume. Testing the official process therefore establishes a
relevant reload capability without changing the production key contract or
exporting an application/ingress Transit key.

## Version-specific Unix permissions and reload behavior

For **2.5.5**, configure all three Unix socket fields together:

```hcl
listener "unix" {
  address      = "/operator-only/api.sock"
  socket_mode  = "0600"
  socket_user  = "<operator numeric UID>"
  socket_group = "<operator numeric GID>"
}
```

Although the individual fields are documented as optional, this version's Unix
listener factory only constructs the permission configuration when **mode,
user, and group are all nonempty**. Setting only `socket_mode` does not exercise
that configuration path. The proof checks the actual resulting socket mode and
owner instead of assuming the settings applied.
[Unix listener documentation for 2.5.x](https://openbao.org/docs/2.5.x/configuration/listener/unix/)
and [2.5.5 listener factory](https://github.com/openbao/openbao/blob/v2.5.5/command/server/listener_unix.go).

The TCP listener reloads the certificate and key from their original configured
paths on `SIGHUP`. Changing those path settings while the process runs does not
redirect the reload. The proof uses atomic replacement at the original
certificate path and signals only its owned process.
[TCP listener documentation for 2.5.x](https://openbao.org/docs/2.5.x/configuration/listener/tcp/).


Its JSON evidence records successful root revocation, scoped authentication
during network TLS expiry, foreign-UID denial, issuer/node-key continuity,
same-process reload, and restored verified TCP access. It explicitly reports
`container_image_qualified: false` and
`customer_reboot_or_auto_unseal_qualified: false`.

The proof does **not** establish the following deployment properties:

- The custom OpenBao image's entrypoint, PID/signal delivery, mount ownership,
  read-only projections, or cross-container socket access policy.
- Customer host boot, process crash, sealed-node recovery, AWS KMS auto-unseal,
  IAM credential refresh, or a multi-node/HA failover.
- Recovery after the PKI issuer, AppRole SecretID, or operator credentials expire;
  this test deliberately keeps those valid while the network leaf expires.
- Public CA issuance or browser trust. Its private test CA is explicitly trusted
  only by the test client.
- Automated scheduling, production activation, rollback, durable installation
  evidence, or a reviewed production recovery authorization.

Those boundaries require their own image and deployment observations before the
operator-socket recovery path can become an accepted installer operation.
