# Supported passport consumer acceptance prerequisite

The supported passport owner is Rust Gateway, Flow, and native issuance. Marty provides the synthetic bureau and KMS callback signer; an external physical provider or CA is not needed for the disposable software proof. Production resources and routing remain unchanged. A Rust-to-Python-to-Rust rollback rehearsal is not a retirement gate.

The protected `passport-supported-consumer-acceptance.yml` workflow inspects existing disposable base Compose, selfhost Compose, and Kubernetes runtimes. Its `marty.passport-supported-consumer-acceptance/v1` receipt remains blocked: the collector observes released images, service readiness, Rust selectors, and a bounded capability probe, but it does not run nine routes or a signed callback. The workflow checks the official release checksum and CD attestations at its protected main commit. Compose projects must use the `marty-passport-acceptance-base-<suffix>` or `marty-passport-acceptance-selfhost-<suffix>` names; the Kubernetes namespace and context must use `marty-passport-acceptance-<suffix>`. A matching name alone does not establish cluster identity or authorize mutation.

The read-only Compose preflight renders the dedicated disposable model and surface overlay. It checks isolated networks and volumes, project-scoped file secrets, pinned image references, and a loopback Gateway edge. The current model still contains an unused legacy Python issuance container and image pin; the Rust-only model change must remove them before acceptance. Gateway and Flow must route to native issuance, and the Marty simulator is selected through the `passport-beta-bureau` profile ID. The selfhost runtime uses beta mode for native issuance because the synthetic simulator is beta-only.

The Kubernetes component at `k8s/passport-supported-disposable/01-simulator.yaml` defines namespace-scoped Marty simulator and callback-signer services with the same native callback target as Compose. The collector requires literal Rust selectors and simulator URLs in both Deployment and ready Pod specifications. It binds run, source, Deployment, ReplicaSet, and Pod identities; permits retained historical ReplicaSets and dual-stack slices; and requires controller-managed ready EndpointSlices whose addresses match the inspected Pods. It rejects host networking, host ports, and external Service IPs. This component cannot establish protected cluster identity or provision the rest of the stack on its own.

The protected provisioning plan binds source, release image digests, owner labels, project, and a short lease. The read-only ownership proof checks exact live container, network, and volume IDs before any project resource can be touched. The current full producer exits before Docker creation, so no accepted ownership record or route evidence is available. An executable producer must verify the plan and model before mutation, initialize isolated KMS and issuer profiles, start the Rust runtime, prove the managed CSCA/DSC chain and nine-route simulator lifecycle on base and selfhost, and verify exact teardown. Kubernetes additionally needs a protected cluster identity and complete isolated runtime. A Rust restart and existing KMS-backed job resume, plus a cutover drain of Python jobs and artifacts, are required before deleting superseded Python passport code.

The `physical_claim` remains `not_claimed`: a simulator receipt proves software route behavior, not physical paperwork or personalization. After Rust parity and protected disposable acceptance pass, delete the superseded Python passport routes and runtime wiring, deploy one aggregate Rust-only beta release, record the demo and acceptance soak, and leave production unchanged. A reusable integration/compliance fixture is optional later work.
