# Supported passport consumer acceptance prerequisite

The protected `passport-supported-consumer-acceptance.yml` workflow inspects existing disposable base Compose, selfhost Compose, and Kubernetes runtimes. Its receipt is `marty.passport-supported-consumer-acceptance/v1` with `status: blocked`. It cannot qualify physical passport Python deletion. The GitHub artifact is named `passport-supported-consumer-acceptance-<run-id>` and contains `passport-supported-consumer-acceptance-<run-id>.json`, matching the retirement verifier's exact run and artifact hash contract.

The collector verifies the official release checksum and CD attestations at the workflow's protected main commit. It accepts only the three expected UI OCI roles and requires all five passport services in each inspected runtime to use the signed services image digest with Rust selectors enabled. Compose targets must be named `marty-passport-acceptance-base-<suffix>` or `marty-passport-acceptance-selfhost-<suffix>`; the Kubernetes namespace and context must each be named `marty-passport-acceptance-<suffix>`. It never inspects `marty-selfhost-prod` or `marty-prod`. A capability HTTP probe is recorded only if Docker inspection proves the requested loopback port belongs to that project's Gateway container. Kubernetes capability probes require a namespace-bound port-forward producer and remain unverified here.

The regular base/selfhost Compose files carry shared networks, build settings, mutable dependency images, and production-specific resources. The read-only model preflight now renders `docker-compose.passport-supported-disposable.yml` plus the matching base or selfhost overlay. Synthetic Docker Compose renders pass its static isolation check for both surfaces: one internal project network, project volumes, disposable file secrets, pinned image references, and a loopback Gateway. The common topology includes the five Rust passport services, signing keys, PostgreSQL, Redis, OpenBao, migrations, and a legacy Python issuance image for a later rollback rehearsal. The `docker-compose.passport-supported-disposable-python-owner.yml` phase overlay changes exactly three Gateway/Flow selectors while retaining the same service topology; tests freeze that delta. No production template is changed.

This is a **static model only**. The Python issuance image needs separate Marty Credentials release provenance. The model does not initialize OpenBao transit keys or issuer profiles, prove any container starts, prove nine routes switch owners and restore, or provide outbound access to a physical bureau from its internal network. A protected provisioner must bind all image digests and secret files to the signed releases, initialize a disposable KMS, and prove Rust-to-Python-to-Rust behavior before this can produce an accepted supported-consumer receipt. Kubernetes still needs an independently governed disposable model and cluster identity proof.

## Required protected provisioning and rollback gate

Rollback transitions are disabled in this collector. Before a separate executable rollback producer can mutate any target, it must first produce and verify a protected provisioning record for each disposable runtime:

1. Record the exact signed release source and OCI image digest, target project or namespace UID, creation run ID, owner label, and cleanup lease. Verify those values against live Docker labels or Kubernetes metadata before each command.
2. For Compose, render the dedicated disposable model and resolved environment for the selected surface and owner phase. Reject external networks and volumes, production bind paths, production database/KMS/provider URLs, shared secrets, and any container outside the named disposable project. Require disposable database, KMS, and callback signer resources under that same project. A physical provider requires a separately governed egress and evidence path. Do not infer safety from the project name or an env-file path.
3. For Kubernetes, verify the dedicated cluster identity against a protected allowlist independently of the caller's context alias. Require acceptance owner labels and recorded UIDs on the namespace and every target Deployment/Pod, isolated Secret/ConfigMap dependencies, and no production database/KMS/provider endpoint. Reject default and production namespaces before any mutation.
4. Capture nine Gateway/Flow routes, managed issuer profile signing, and callback protocol before transition. Execute a bounded Rust-to-Python selector change only in the verified disposable target, observe replacement container/pod identities and the expected legacy route behavior, then restore Rust ownership and rerun the same probes. Publish failed/partial transitions as blocked; clean up the disposable resources by recorded UID after the run.

A physical-booklet test also needs independent provider evidence tied to the same release and runtime. A simulator or signed callback protocol receipt cannot establish that a physical passport was personalized. The retirement verifier intentionally rejects an accepted report until this producer and provider proof receive separate maintainer review.

## Read-only Compose ownership proof

`scripts/check_passport_supported_compose_ownership.py` checks an already running disposable base or selfhost project against a short-lived provisioning record. The record names the exact project, protected run ID, source commit, signed services image, container IDs by service, network names and IDs, volume names, and creation/expiry times. The project, every container, network, and volume must carry matching Compose project and `com.marty.passport.acceptance.*` ownership labels. The live project resource sets must equal the record. Every container must have a project-scoped Compose service name, use only recorded internal project networks and volumes, and the five passport services must use the signed image. The passport and dependency services must be running and healthy where a healthcheck exists; only named migration/init roles may be exited successfully. It records only a blocked result, even when all read-only checks pass.

The record is caller supplied and is **not** a protected provisioning attestation. No checked-in workflow currently creates a protected resource record. The regular base and selfhost Compose sources cannot pass the resolved-model preflight; the dedicated disposable models can pass its static check. A protected provisioner that labels and records every resource, source-bound signed images for both Marty UI and Marty Credentials, and an actual Rust-to-Python-to-Rust route rehearsal are still required. Neither this proof nor the existing collector qualifies the retirement gate or authorizes cleanup.

## Protected plan and record boundary

The protected `passport-supported-provisioning-plan.yml` workflow runs on a hosted runner from `main` under `beta-lifecycle`. It downloads an official UI stack release at its exact workflow commit. `scripts/passport_supported_provisioning_plan.py` checks the manifest checksum and UI CD attestations, then verifies the Marty Credentials issuance OCI attestation at the component's exact release tag and commit. The source-controlled `deploy-config/passport-supported-disposable-infra-images.json` pins PostgreSQL, Redis, and OpenBao to reviewed OCI index digests for `linux/amd64`; the plan checks each registry index and binds these exact references. The read-only Compose renderer overrides caller env-file infrastructure refs with the checked-in pins. The plan derives a disposable project from the protected run ID and a random nonce, binds all released and infrastructure image roles, and emits a two-hour **blocked** plan. The workflow attests and uploads this plan. It has no Docker mutation command and reads no runtime secrets.

`scripts/check_passport_supported_provisioning_record.py` requires both the plan and a future resource record to have GitHub attestations from the exact protected plan and hosted record-attestor workflows at the same main source commit. It rejects changes to the plan digest, project, lease, run ID, UI services/migrations, legacy issuance, or infrastructure image references and owner labels before invoking the #911 live ownership proof. That proof requires the exact bound image on live Gateway, Flow, native issuance, callback signer, provider ingress, signing keys, migration, legacy Python issuance, PostgreSQL, Redis, and OpenBao containers. Its result remains blocked even if that read-only proof passes.

The hosted `passport-supported-provisioning-record.yml` attestor has no Docker access. The protected manual `Passport Supported Disposable Provisioning Producer` entrypoint now exists, but deliberately exits nonzero before any Docker mutation or record upload. It checks the exact successful plan workflow/run and source through the GitHub API, verifies the plan attestation and official release, then checks the clean source checkout and short lease. Its model and record helpers can render exact plan-bound labels on every disposable service, network and volume, then gather live IDs and run the read-only ownership proof. None of those helpers is wired to Docker creation or removal. The hosted attestor therefore remains dormant: it only signs a successful same-commit producer artifact, which this blocked producer cannot emit.

The read-only rollback preflight CLI reports `model_safe: false` without `--plan`. With `--plan`, it verifies the protected plan attestation, lease, exact checked-out source commit, and clean checkout before rendering and comparing the exact eleven service roles, owner labels and every released or reviewed image reference; its result remains blocked. A future producer must keep plan, env and secret artifacts outside the checkout so this clean-source check remains meaningful. Before Docker creation, that producer must call `verify_pre_mutation` to verify the release manifest checksum/source and attested model. The `validate_planned_model` helper alone checks no attestation. The live ownership proof also requires the exact eleven-service set and matching labels. A future cleanup operation must use the same verified project and resource IDs within the lease and cannot target shared resources.

Live provisioning still needs governed beta-lifecycle secret files, a disposable issuer profile and physical provider binding, and an OpenBao transit bootstrap. The pinned OpenBao image currently defaults to development mode; this scaffold does not create transit keys or reimplement the separate KMS hardening branch. The producer must demonstrate controlled KMS initialization, startup, bounded teardown, actual Rust-to-Python-to-Rust nine-route restoration, and physical provider evidence before any supported-consumer acceptance or Python deletion. Production remains untouched.
