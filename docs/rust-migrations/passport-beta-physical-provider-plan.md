# Physical-provider beta passport plan

This is a separate, default-off variant of the beta Rust passport profile. The existing `docker-compose.profile.passport-native-beta.yml` remains the synthetic bureau test path. Select the physical variant only with both `-EnablePassportNative` and `-EnablePassportPhysicalProvider` in `deploy-local-beta-release.ps1 -PlanOnly`. The physical plan composes `docker-compose.profile.passport-provider-base.yml` followed by `docker-compose.profile.passport-native-physical-beta.yml`; it selects exactly gateway, flow, issuance-native, signing-keys, passport-callback-signer-supported, and passport-provider-ingress. It never selects `passport-beta-bureau` or `passport-callback-signer`.

The physical profile requires an HTTPS bureau endpoint and a registered provider profile ID. Issuance submits with a file-backed provider API credential. A private provider ingress verifies the physical bureau webhook and forwards the signed callback to issuance-native. The callback signer runs the **beta-only** signer binary under the ingress's private `passport-callback-signer-supported` DNS name. It uses the shared Rust KMS MAC router, dedicated file-backed API key and scoped OpenBao token, and local beta OpenBao. Its `ENVIRONMENT=beta` guard remains intact. The provider ingress and signer have no host ports. The configuration validator rejects simulator names, raw artifact keys, remote document signer, self-signed document mode, missing managed issuer/KMS selectors, mismatched provider identity, and secrets outside a beta-only `elevenid-beta-passport-physical` directory.

The secret directory must contain distinct, non-development files named `passport_physical_provider_api_key`, `passport_provider_webhook_secret`, `passport_callback_signer_api_key`, and `passport_callback_signer_bao_token`. The callback token needs only the callback HMAC policy. The validator can check file presence and isolation; a later live gate must verify the token's **effective** OpenBao capabilities and the provider profile's registration. The managed CSCA and DSC issuer profiles remain the source of ICAO signing. No external CA is assumed.

The source-controlled `deploy-config/passport-beta-physical-provider-allowlist.json` is currently `blocked` with no provider. The validator requires an approved record binding the exact endpoint and profile ID to a physical beta provider. Adding that record requires a reviewed protected source commit and a signed release built from that commit; an arbitrary HTTPS URL or a `physical` label is insufficient. No provider has been approved yet. The validator also requires the exact `elevenid-beta` Compose project, its private signing network, expected network membership for all six services, and beta-only secret mounts. It rejects host networks, shared volumes, container names, inherited volumes, and production-like secret paths.

Actual physical-mode deployment and restore are blocked. `deploy-local-beta-release.ps1` throws before reading deployment state unless `-PlanOnly` is set. `restore-local-beta-release.ps1 -PhysicalProviderSnapshot -PlanOnly` emits a blocked restore plan; its existing simulator restore path is unchanged. A live physical bureau, source-bound acceptance, tested provider drain and rollback, and maintainer review are needed before either mutation path can be enabled. Production is untouched.

The current beta evidence collector and physical-passport Python retirement verifier still expect the simulator service names. Before physical acceptance can qualify deletion, they must be restacked to use the six physical service names above, prove simulator absence, and bind the provider ingress receipt to the same protected source and immutable image. The #908 provider-ingress projection must be reconciled with that physical-mode schema. This profile does not claim physical booklet acceptance.
